# 下一階段規劃：文案精修、圖片檢視、防拷調查、配藥小遊戲

狀態：**規劃中，未動工。** 每項的執行條件與時間盒寫在各節末。

---

## 0. 先講三個會影響全盤的前置發現

**① 這款遊戲很可能沒有可以「關掉」的防拷關卡。**
掃過全部 5,181 則文字，找不到任何「輸入手冊第 N 頁某字」「回答問題才能繼續」型的 gate；
命中的字串全是遊戲內玩笑（連環殺手、梯子編號）或 Sierra 制式文案（更換磁片、提示專線）。
這與 `docs/manual-highlights.md` 記載一致：**防拷是融進劇情的**——顧客拿處方箋上門，
玩家得翻實體手冊查配方、劑量、單位，沒有手冊配不出藥。
**推論**：沒有東西可以「關閉」；真要關，等於把遊戲的核心解謎拿掉。這一項需要 subagent 正式查證（見 §4）。

**② 因此「防拷小遊戲」與「配藥小遊戲」是同一個東西。**
防拷機制 = 查手冊配藥。把它做成網頁小遊戲，一支就同時滿足兩個需求，不必做兩支。
這是規劃階段最重要的簡化。

**③ README 目前缺的不是文筆，是「證據」。**
現在四張截圖都在證明「有中文」，但沒有一張證明「翻得好」或「原本長怎樣」。
而我們手上**已經有**最有說服力的素材沒放進去（見 §3）。

## 1. 遊戲推廣文案：從業界指南萃取的可套用準則

來源：[Steam Page Analyzer 的描述撰寫指南](https://www.steampageanalyzer.com/blog/steam-description-writing-guide)、
[presskit.gg 的 Steam 描述 field guide](https://presskit.gg/field-guides/steam-description-guide)、
[IndieDB 的遊戲描述教學](https://www.indiedb.com/tutorials/how-to-write-a-kickass-game-description)。

| 準則 | 原文要旨 | 套到本專案怎麼用 |
|---|---|---|
| **開頭三拍** | 你做什麼／有何不同／感覺如何 | 「1993 年那張廣告上的遊戲，現在整套是中文的，而且現在就能裝」 |
| **具體勝形容詞** | 「hand-painted watercolor environments that shift with seasons」勝過「stunning visuals」 | 不寫「完整中文化」，寫「5,166 / 5,181 則、倚天點陣字 2,889 個字」 |
| **黑名單詞** | immersive、unique、epic、stunning、amazing、experience、journey | 中文對應：沉浸、獨特、史詩、驚豔、極致、完美、大幅提升 |
| **條列要有數字** | 4–6 條，每條一個完整想法，帶具體數字 | 現有條列已接近，但「涵蓋範圍不只主線對白」那條太長，該拆 |
| **不要道歉** | 不寫「還在 Early Access 但…」 | 「已知限制」該放後段，不要在開頭稀釋主張 |
| **不要開發流水帳** | 技術規格與開發背景不放前段 | 「技術做法」那節位置正確，但別讓它跑到特色之前 |
| **朗讀測試** | 唸起來卡就是句子太長 | 交稿前整份唸一遍 |

**與本專案既有文風規則的關係**：這些準則和 `rulebook/90`（白話七準則）、`91`（去 AI 味）方向一致，
不衝突。差別在於這幾條更偏「轉換率」——先給理由再給故事。
但**本專案的 README 不是 Steam 商店頁**：讀者不是在挑遊戲，是在決定要不要裝這個 patch。
所以「三拍」要調成：**這是什麼 → 為什麼值得裝 → 怎麼裝**。故事保留，但不能擋在最前面。

## 2. README 重新檢視

**現況診斷**（對照 §1 準則）：

| 問題 | 位置 | 建議 |
|---|---|---|
| 故事開場很好，但「這是什麼、值不值得裝」被推到第 76 行 | 開頭 | 標題下加 3–4 行的**主張區塊**（一句定位 + 三個數字 + 一張對照圖），故事往後移一節 |
| 沒有「安裝要幾分鐘」的預期管理 | 安裝節 | 開頭補一句「自備遊戲的話，三分鐘內可以開始玩」 |
| 「涵蓋範圍不只主線對白」單條塞了 7 個項目 | 特色條列 | 拆成兩條，或改成一行短表 |
| 已知限制有 5 條，其中 3 條是「原版就這樣」 | 已知限制 | 分成「刻意保留原版風貌」與「技術限制」兩組，避免讀起來像缺陷清單 |
| 沒有任何一句話說明「為什麼值得為一款 1993 年的遊戲做這件事」 | 全篇 | 廣告那節其實已經回答了，但沒有把話點破 |

**不動的部分**：故事前言（已核對過遊戲原文，事實正確）、廣告引用（來源與界線已處理）、
版權節、技術做法節。

**誰做**：主 session 自己改（文案是判斷密集、來回修的工作，派 subagent 反而要多輪對稿）。
**時間盒**：一次改完出一版，最多再修一輪。**不進第三輪**——第三輪通常是在改自己的偏好，不是改品質。

## 4. 防拷調查（派 subagent）

**任務**：確認《多情藥師酷牛仔》是否存在可程式化繞過的防拷關卡。

**subagent 要做的**（model：sonnet，機械查證）：
1. `SCI_DUMP_RES` dump `heap.*` / `script.*`，找是否有 `kStrCmp` / `kStrEnd` / parser 型的答案比對。
2. 對照 §0① 的初步結論——文字層找不到 gate，但**字串可能是 runtime 組出來的**（SQ4 狀態列就是這樣）。
3. 實機驗一次：拿一張處方箋，不看手冊隨便配，看遊戲怎麼反應（是「配錯有後果」還是「擋住不讓過」）。
4. 產出 `docs/copy-protection-findings.md`：有沒有 gate、在哪個 script、若要繞過該 hook 哪個 kernel。

**明確不要做**：不要改引擎、不要套 patch、不要 commit。只調查、只寫報告。
**邊界**（寫進 prompt）：只在 `workplace/` 內讀寫；docker 一律 `--name freddy-cp-*`、收工只刪自己那些；
**禁止任何 image/volume/system prune 或 rmi**；不碰 `dist-all/`、不碰別的專案目錄。
**時間盒**：40 分鐘。查不出來就回報「查到哪裡、卡在哪」，不要無限深入。

**決策點**：若確認「沒有可關閉的 gate」，則「在遊戲中關閉防拷」這項**取消**（沒有東西可關，
硬關等於拿掉核心解謎），改為在 README 說明「本作的防拷就是手冊，我們把手冊翻成中文了」——
這反而是個好賣點。

## 5. 配藥小遊戲（GitHub Pages）

**定位**：一支網頁小遊戲，重現「收處方箋 → 查手冊 → 秤重調配 → 交藥」的循環。
它同時就是「防拷小遊戲」（§0②）。

**為什麼值得做**：`docs/manual-highlights.md` 已經整理好 73 條藥品、7 則完整配方（成分、劑量、單位、步驟），
那是現成的遊戲資料，不必再逆向。這是這個點子成本最低的原因。

**範圍（第一版，刻意小）**：
- 3–5 張處方箋，全部取自手冊已整理的配方
- 介面：處方箋 → 可翻查的中文手冊 → 器材台（秤重／加熱／攪拌／分裝）→ 交藥評分
- 純靜態 HTML/CSS/JS，無後端，放 GitHub Pages
- 中文介面，倚天風格的點陣字可用 CSS `image-rendering: pixelated` 模擬，或直接用網頁字型

**[HARD] 版權界線（動工前必須先解決，否則不要開始）**：
- **不得使用遊戲原始美術**（背景、器材、人物都是 Sierra／Activision 的著作）。
  → 第一版用自繪的簡單向量／CSS 圖形，或純文字介面。
- **手冊配方文字**：手冊是 Al Lowe 的著作。我們的中文重點索引是**改寫整理**而非逐字轉錄，
  用於自製小遊戲屬於再利用，需要先確認界線。**這一條要先問使用者。**
- 頁面須標明：致敬原作、非官方、與 Sierra／Activision 無關。

**誰做**：
- 遊戲邏輯與資料（配方 JSON、判定規則）→ subagent（sonnet），有明確規格可寫。
- 介面設計與美術方向 → Designer subagent（依 CLAUDE.md ⑦，美術不自己硬幹）。
- 整合、GitHub Pages 設定、版權文案 → 主 session。

**時間盒**：規格定稿後，第一版 subagent 一輪產出可跑的原型；**不做第二輪功能擴充**，
先讓使用者玩過再決定要不要繼續。

**前置條件（未滿足前不動工）**：
1. §4 的調查結論出來（確認這支小遊戲的定位要不要調整）
2. 版權界線由使用者拍板（尤其手冊配方的再利用）
3. 使用者確認要做（這是新專案級的工作量，不是 README 修訂那種尺度）

## 6. 建議執行順序與迴圈防護

| 順序 | 工作 | 誰 | 估時 | 可否平行 |
|---|---|---|---|---|
| 1 | 防拷調查 | subagent (sonnet) | 40 分鐘（時間盒） | ✅ 與 2、3 平行 |
| 2 | README 文案精修 | 主 session | 一輪 | ✅ |
| 3 | 圖片重選與重切 | 主 session | 30 秒產圖 + 目視 | 與 2 綁在一起做 |
| 4 | 小遊戲 | 待前置條件 | — | ❌ 等 1 的結論 |

**迴圈防護（本次特別要求，也是上一輪的教訓）**：
- **每項都有時間盒**，到點就回報現況，不自行延長。
- **文案不進第三輪**：第三輪通常是在改偏好不是改品質。
- **subagent 只調查不改碼**，回報後由主 session 決定下一步——避免「agent 自行加碼」。
- **任何「再試一次」之前先問：我是否已經看過完整證據？** 上一輪三次誤判都是跳過這一步。
- **回饋迴圈慢的工作（實機驗證），動手前先想清楚**；快的工作（改文字）可以多試。
