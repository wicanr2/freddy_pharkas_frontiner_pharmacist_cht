## 2. 片長與影像規格

### 片長

**62 秒**，第 5 節逐鏡時間總和即為此數，兩者必須永遠一致。改動任何一鏡的秒數，
表格底部的合計欄要同步改，不接受「大約」。

### 為什麼 master 是 1920×1080 而不是 1280×720

遊戲畫面是 **640×400**（SCI 原生 320×200，繁中路徑強制 `GFX_SCREEN_UPSCALED_640x400`）。
點陣畫面只有整數倍放大才不會糊，所以規格從「2× 放得下嗎」倒推：

| 候選 | 遊戲畫面倍率 | 問題 |
|---|---|---|
| 1280×720 | 2× 是 1280×800，**高度超出** | 只能 1.5×（960×600）→ 非整數，邊緣糊；第一版寫「不會糊」是錯的 |
| 1280×800 | 2× 剛好滿版 | 沒有版面空間放字幕與對照，且 16:10 在多數平台會被上下加黑邊 |
| **1920×1080（採用）** | 2× = 1280×800 置中 | 上下左右留白足夠放字幕帶與對照版面，且是平台原生尺寸，不必再縮放 |
| 1920×1200 | 3× = 1920×1200 滿版 | 完全沒有版面空間，且 16:10 |

**採用 1920×1080。** 所有遊戲畫面一律 **2× nearest-neighbor**，不做任何非整數縮放。

### 版面幾何（固定值，做的時候不要再自己算）

| 用途 | 來源尺寸 | 放大 | 成品尺寸 | 位置 |
|---|---|---|---|---|
| 單畫面 | 640×400 | 2× nearest | 1280×800 | 置中 (320, 100)，下方 180px 為字幕帶 |
| 左右對照（每側） | 448×400 裁切 | 2× nearest | 896×800 | 左 (16, 100)、右 (1008, 100)，間距 96px |
| 廣告掃描 | 非點陣，自由縮放 | 等比 | 貼齊 896×800 或全幅 | 不足處填設計底色 |

對照鏡為什麼只取 448×400 而不是整張：兩塊 1280×800 放不進 1920。裁切到 448 寬、
放大 2× 之後兩塊剛好排得下，而且畫面主體（店面、角色、對白框）都在中間，裁掉的是兩側背景。
**裁切區要逐鏡目視確認主體沒被切到**，不是套公式。

### 其他影像規格

| 項目 | 值 | 說明 |
|---|---|---|
| fps | **30** | 側錄與輸出都用 30。若實錄後發現 SCI 的動畫更新率讓 30 出現規律掉幀，再改 25 並在此註記 |
| 編碼 | H.264 `yuv420p`，`-preset veryfast -threads 2` | promo 不需要慢 preset |
| 縮放旗標 | ffmpeg `scale=…:flags=neighbor`／IM `-filter point` | 一律明寫，不靠預設值 |
| 轉場 | 0.5 秒 fade；對照鏡用推入 | 不用 zoompan（kb `game-promo-video-ffmpeg` 雷 #1：幀數爆炸） |
| 音訊 | AAC 192k；`aloop` 循環後 `atrim` 到片長 | 不加 `-shortest`（同 kb：會砍掉結尾卡） |

## 4. 鏡頭型態：still 還是 live

第一版整支都是靜態圖，被判定不足以稱為宣傳影片。這一版的規則：

- **廣告掃描一律 still**（它本來就是印刷品，動起來反而假）。
- **遊戲畫面原則上 live**，用 `ffmpeg -f x11grab` 實時錄 Xvfb 畫面，不是把截圖排成投影片。
- 全片 **7 段 live**，佔 44 秒（總長 62 秒的 71%）。#1 與 #5 是左靜右動的對照鏡，右半是實機錄影，計入 live。
- 逐鏡在第 5 節的「型態」欄標明，不留模糊地帶。

### F8 那一鏡的特別注意

引擎的 F8 是**下一則訊息才生效**（切換的是後續繪字路徑，不會回頭重畫已經在螢幕上的對白框）。
所以「現場按 F8」的鏡頭不能只按一下就等畫面變，必須是：

```
中文對白顯示 → 關掉對白框 → 按 F8 → 重新點同一個熱點 → 同一句以英文出現 → 再按 F8 → 再點 → 中文回來
```

錄的時候要把這串操作壓進 7 秒內，節奏靠 xdotool 的 sleep 調。
**這鏡是全片最有說服力的功能鏡頭，值得多錄幾次挑一條最順的。**

## 6. 當年的廣告怎麼入鏡

廣告是骨架不是裝飾，三種用法：

1. **鉤子**（#1）：不先解釋，直接把廣告那格和今日畫面並排。看得懂的人 0.5 秒就懂了。
2. **脈絡**（#2）：這時才回頭交代這張圖是什麼、哪一年、哪本雜誌。
3. **對照**（#5）：第二組對照，讓「這不是單一巧合，是整套都做了」這件事成立。

處理原則：只裁切與等比縮放，**不加濾鏡、不去背、不改字、不重繪**。要標示一律用畫面外的小標。

## 8. 配樂與引用策略

### 原則（本專案版本）

`rulebook/93` 的鐵則是「配樂用原版真實素材、不可自產」，但同一份規則的但書寫明：
公開影片配上原版音樂等於散布他人著作，要先讓人決定，可能改用授權曲。
這支片預設公開，因此走但書那條路。修訂後的原則是：

> **畫面必須真實**（一律引擎實機，不用 mockup、不重繪、不用 AI 生成畫面）；
> **配樂以「可合法公開」為最高優先**，在此前提下才挑最貼近西部氛圍的曲子。

這不是放寬對素材真實性的要求，而是把「真實性」的適用範圍講清楚：真實性管畫面，合法性管音樂。

### 公開版配樂：CC0 或 CC BY 的西部風配樂

| 項目 | 要求 |
|---|---|
| 授權 | **CC0** 或 **CC BY**，且明確允許商用與再散布（影音平台的營利化與轉載都算） |
| 證據保存 | 下載頁快照、授權條款全文、作者與曲名，一併存進 `out/video_src/music/LICENSE/` |
| Attribution | CC BY 必須在片尾與發布說明兩處標示；CC0 也標，成本低而爭議少 |
| 排除 | NC（禁商用）、ND（禁改作）一律不用——影片會裁剪與淡入淡出，屬於改作 |

**原版 MT-32 側錄與 CD 演唱錄音都不進公開版。** 本機懷舊版（配上原版音樂、只留在
`out/video/local/`、永不上傳）如果要做，另案處理，不能成為主流程的依賴——
也就是說，主片的製作流程不可以有任何一步需要先產出懷舊版。

### 遊戲音效

只取必要的極短片段（例如一次開門聲、一次翻頁聲），用於強調操作，總長控制在 3 秒以內，
且不與配樂搶。若審稿認為連短音效都不要，全片純配樂也成立，不影響其他段落。

### 廣告與遊戲畫面的引用

這是**風險控制策略，不是法律結論**。這份提案不主張片子因此當然構成合理使用。

- 廣告只用短句與局部裁切，保留史料與評論的脈絡（片中明確標示年代、出處、以及「當年沒有中文版」的對照關係）。
- 不使用第 114–115 頁的評測掃描頁（整頁文章，超出短引用範圍）。
- 片尾與每個發布管道的說明欄都要有來源與權利聲明，內容至少涵蓋：遊戲版權屬 Sierra On-Line／Activision、
  廣告版權屬《軟體世界》與原刊、本片為非商業的粉絲中文化專案介紹、配樂授權與 attribution。
- 遊戲畫面本身是 Sierra／Activision 的著作。粉絲中文化專案放實機畫面是慣例，但慣例不等於授權；
  上傳到會自動比對版權的平台之前，這一點要和配樂一起評估。

## 9. 製作流程

三段式，每段一支腳本、輸入輸出都是檔案，可重跑。

### 前置：需要一顆帶 ffmpeg 的擷取 image

實測結果：`freddy-capture:latest` **沒有 ffmpeg**（有 Xvfb／xdotool／ImageMagick／ScummVM runtime），
`game-video:latest` 有 ffmpeg 與 x11grab 但沒有遊戲執行環境。live 錄影需要兩者在同一個容器裡。

做法：以 `freddy-capture:latest` 為基底 `apt install ffmpeg qrencode`，`docker commit` 成
**`freddy-video-capture:latest`**，之後零安裝。這是本專案自建的新 image；
**不動任何既有 image，不執行任何 prune 或 rmi。**

### 第一段：擷取（`tools/cap_promo.sh`，待寫）

```bash
docker run --rm --name freddy-video-cap-<鏡號> --cpus=2 \
  -v "$PWD":/w -w /w freddy-video-capture:latest bash -c '
    Xvfb :99 -screen 0 1280x800x24 & sleep 2
    ./scummvm-src/scummvm --config=/tmp/scummvm.ini freddypharkas &
    sleep 25
    ffmpeg -f x11grab -framerate 30 -video_size 1280x800 -i :99 -t <秒數> \
           -c:v libx264 -preset ultrafast -qp 0 /w/out/video_src/raw_<鏡號>.mkv &
    <xdotool 操作序列>
    wait
  '
```

- 錄影用 `-qp 0` 無損中間檔，壓縮留到合成階段；中間檔不入版控。
- 場景用除錯器換（`Ctrl+Alt+D` → `room N`），不玩劇情；第 7 鏡例外（見第 7 節風險）。
- **[HARD]** 一律 `timeout` 包住；收工只 `docker rm -f freddy-video-*`，不碰別人的容器與 image。

### 第二段：素材（`tools/mk_promo_assets.sh`，待寫）

在 `game-video:latest` 裡用 ImageMagick／ffmpeg 生成：


## 13. 驗收標準

**素材真實性**
- 每一格遊戲畫面都是引擎實機擷取或實機錄影，沒有設計稿、沒有 mockup、沒有重繪、沒有 AI 生成畫面。
- 中文畫面用的是 v1.0 的 `translation.tsv` 與字型（md5 對得上 `dist-cht/`）。
- live 段落確實是錄影而非截圖排列：抽查任一 live 段的相鄰兩幀，畫面內容必須不同。

**影像技術**
- 所有遊戲畫面的放大倍率為整數，且縮放旗標明寫 `neighbor`／`-filter point`；輸出檔中不存在非整數縮放的遊戲畫面。
- `ffprobe` 確認成品為 1920×1080、30 fps，視訊與音訊長度差 < 0.1 秒，結尾卡沒有被砍。
- 逐鏡秒數總和 == 成品實際長度（62 秒），誤差 < 0.2 秒。

**音訊**
- `volumedetect` 的 `mean_volume` 不是 -91 dB（靜音）、`max_volume` < 0（沒有削波）。
- 配樂授權檔與 attribution 文字都在位；成品中不含原版 MT-32 或 CD 錄音。

**內容**
- 沒有劇透：不出現結局、死亡畫面、分數結算、幕後主使、任何謎題的解法。
- 片中所有中文沒有錯字；片尾數字逐一對過 README。
- 片尾與各發布管道說明欄都有來源與權利聲明。
- 實體手機掃 QR 一次成功並開啟正確頁面。

**工程衛生**
- 合成全程 docker、`--cpus=2`、沒有 zoompan 幀數爆炸。
- 收工後 `docker ps -a | grep freddy-video` 為空；沒有動到任何非本專案的容器或 image；沒有執行過任何 prune／rmi。
- `out/video/`、`out/video_src/` 未進版控，`git status` 乾淨。
